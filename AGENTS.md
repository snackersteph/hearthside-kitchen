# Project rules
- Shared visual styling belongs in global semantic tokens and scoped shell selectors, with control variants in shared UI components; page behavior and kitchen state stay independent of theme changes.
- Recipe types are derived by the shared recipeType helper unless staff save an explicit selection; they are separate from main/side/snack and never alter dietary analysis.
- Showcase profile changes and observations use a one-time additive demo-content migration with internal demo flags; preserve staff reviews and resident records rather than fabricating care edits.
- Account rules: src/components/AGENTS.md.
- Agent logic (Dietary/Menu/Inventory) lives in the pure `analyze()` in src/lib/kitchen/engine.ts; proposals are derived from state, so pages never store them — keeps agents sharing one context and re-running on every change.
- Staff decisions are the only persisted actions (history + overrides + onOrder), stored in localStorage via KitchenProvider until a backend is added.
- Engine rules are covered by src/test/kitchen-engine.test.ts; update it when safety rules change.
- Menu and inventory use the shared schedule helpers; analyze derives horizon demand and purchasing requests so forecasts cannot diverge from the displayed sample rotation.
- Date-specific future main dishes are staff decisions stored in KitchenState.scheduledPlans; the shared schedule resolves them before the sample rotation so editing one day changes only that day's forecast.
- Approved purchases remain incoming until explicitly received; dated order lines support delivery-aware forecasts without treating unreceived stock as available today.
- Stock-alert orders use shared validation and estimates; edits and receipts synchronize incoming quantities without adding stock until receipt.
- Preserve Kitchen context identity through Vite hot updates so mounted providers and refreshed consumers cannot split into different contexts.

- Meal views, resident alternatives and forecasts use analyzeMenuDay with date-scoped decisions; whole-meal sign-off checks a plan/profile signature and the day-before deadline so future approvals cannot affect another service or survive changes.
- KitchenProvider renders operational pages only after the browser calendar is available and refreshes its clock each minute to avoid server/browser timezone mismatches in deadlines.
- Whole-meal rejections are signature-scoped staff decisions; replacing the plan reopens review, while service-day approved meals are locked in the review editor.
- Menu review links carry service date and meal search filters so pending and approved reviews resolve to the exact service.
- Daily Menu uses a date overview and an un-nested dated detail route with shared meal sections, so date navigation and meal tabs reuse existing review and editing behavior.
- Pre-bundle newly used hook-based UI dependencies in Vite to prevent mid-session dependency optimization from loading a second React instance.
- Approval Center derives approved alternatives from dated overrides and pending alternatives from analysis; main meal sign-off cards are not rendered there.
- Saved alternative authorizations are resident/main-dish/meal-scoped and signed against food requirements; resolveMenuState derives safe approved servings for every view and forecast without persisting generated daily decisions, while requirement changes revoke authorization and affected current/future overrides.
- Resident and ingredient creation use validated reducer actions and the existing KitchenProvider persistence so new entries immediately participate in dietary analysis and inventory forecasts.
- Uploaded resident care information is retained verbatim alongside supported engine categories; versioned catalog replacements clear previous resident-specific authorizations without resetting inventory or purchasing history.
- Residents use a table index and un-nested profile detail routes with a shared editing dialog, so navigation preserves complete profiles and existing staff actions.
- Fictional resident portraits are keyed by resident ID in a shared photo component so table thumbnails and profile portraits remain consistent without changing stored care records.
- New resident photo uploads are resized in the browser and stored with the resident using existing demo persistence; the shared photo component prefers uploaded portraits so list and detail photos match.
- Resident deletion uses the shared reducer to remove the profile and resident-scoped meal choices while preserving decision history and purchasing records.
- Additional resident batches use one-time additive migrations so saved edits, deletions, and staff decisions remain intact.
- Inventory edits use validated reducer actions; deletion tombstones prevent catalog restoration, and missing recipe ingredients remain visible as forecast shortages.
- Command Center card totals and observation board filters come from src/lib/kitchen/overview.ts so a card's actionable and peaceful states always match stored state.
- Inventory view search parameters deep-link delivery cards to their order tabs; delivered work counts due unconfirmed receipts rather than archived orders.
- Resident meal history derives only from dated staff menus, resident overrides and meal observations; never present generated rotation or current dietary decisions as historical consumption.
- Recipe library seeds from generated recipe-catalog.ts; state.recipes override by id, deletions tombstoned; g/ml convert to kg/L. Menu DISHES derive from catalog main recipes; legacy ids map via currentDishId/migrateMenuDishes; halal/vegan needs come from careProfile Diet Type.
